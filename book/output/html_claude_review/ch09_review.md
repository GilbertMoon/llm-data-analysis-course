## 0. GPT 재검토 요약

ch09는 LLM 프롬프트 기반 분석 보조를 다루는 장으로, 데이터 원본을 그대로 넣지 않고 구조 요약·집계 결과·오류 메시지·분석 목적을 이용해 LLM에게 질문하는 방향이 잘 잡혀 있습니다. 특히 개인정보·거래 상세 원본·API Key·비공개 문서를 LLM에 넣지 말라는 안내와, 나쁜 프롬프트/좋은 프롬프트 비교, LLM 답변 검증 체크리스트는 교육적으로 타당합니다.

다만 Claude 리뷰의 일부 항목은 실제 본문을 감안하면 “필수 수정”으로 보기에는 과합니다. 특히 CSV 인코딩, `base_dir` 자동 감지 고도화, `to_csv(index=False)` 문자열 반환 설명, `line_total` 재생성 방어, 특정 LLM 도구 안내, 코드 펜스 방식 등은 보완하면 좋지만 본문 오류로 단정하기 어렵습니다.

## 3. 보완 권장으로 낮출 항목

### [3-1] CSV 저장 시 인코딩 안내

**판단**  
보완 권장입니다.

**이유**  
분석 코드 실행에는 문제가 없지만, Windows Excel에서 한글 CSV를 열 경우 깨질 수 있습니다. 초보자가 Excel로 결과를 확인하는 수업이라면 `utf-8-sig` 안내를 추가하는 것이 좋습니다.

**보완 방향**

- “Excel에서 한글이 깨지면 `encoding='utf-8-sig'` 옵션을 사용할 수 있습니다” 정도의 주석을 추가합니다.
- 모든 저장 코드에 일괄 강제하기보다는 결과 확인 방식에 따라 선택 안내로 두는 것이 적절합니다.

---

### [3-2] `to_csv(index=False)` 문자열 반환 설명

**판단**  
보완 권장입니다.

**이유**  
원문에는 이미 “LLM 입력용 텍스트로 변환합니다”라는 설명이 있습니다. 다만 초보자는 `to_csv()`가 항상 파일 저장이라고 오해할 수 있으므로 한 줄 설명을 추가하면 좋습니다.

**보완 방향**

- `to_csv()`에 파일 경로를 넣으면 파일 저장입니다.
- 파일 경로 없이 호출하면 CSV 형식의 문자열을 반환합니다.
- 이 방식은 원본 데이터 전체가 아니라 집계 결과처럼 안전한 요약 데이터에만 사용합니다.

### [3-3] `line_total` 컬럼 존재 확인

**판단**  
보완 권장입니다.

**이유**  
ch05 전처리 흐름을 정상적으로 수행했다면 `line_total`이 존재하는 것이 자연스럽습니다. 다만 학생이 중간 장을 건너뛰거나 전처리 파일을 다시 만들지 않은 경우 `KeyError`가 발생할 수 있으므로, 실습 안정성을 높이는 보완으로는 타당합니다.

**보완 방향**

- `line_total`이 없으면 `quantity * unit_price`로 다시 만들 수 있다는 설명을 추가합니다.
- 단, 필수 수정이라기보다는 실습 방어 코드입니다.

### [3-4] LLM 답변 예시와 검증 과정 추가

**판단**  
보완 권장입니다. 다만 교육 효과 측면에서는 우선순위가 높습니다.

**이유**  
ch09의 핵심 메시지는 “LLM 답변을 사람이 최종 검증한다”입니다. 현재도 검증 필요성과 체크리스트는 잘 설명되어 있지만, 실제 잘못된 LLM 답변 예시와 수정 과정을 하나 보여주면 학습 효과가 크게 올라갑니다.

**보완 방향**

- 예: LLM이 `order_items`에 없는 `category` 컬럼을 바로 사용한 코드 제안
- 검증: 실제 컬럼 확인 결과 `category`는 `products`에 있으므로 `product_id` 기준 병합 필요
- 수정: 병합 후 `groupby('category')` 수행

---

### [3-5] `.format()` 문법 설명

**판단**  
보완 권장입니다.

**이유**  
프롬프트 템플릿을 채우는 데 `.format()`을 사용하므로 초보자에게 간단한 설명이 있으면 좋습니다. 다만 Python 문법의 세부 설명이므로 필수 오류는 아닙니다.

**보완 방향**

- `{analysis_goal}` 같은 부분은 나중에 값이 들어갈 자리 표시자입니다.
- `.format()`은 같은 프롬프트 구조를 여러 번 재사용할 때 편리합니다.
- f-string은 이미 변수에 값이 있을 때 일회성 문장을 만들기에 편리합니다.

## 4. 참고 또는 선택 보완 항목

### [4-1] `base_dir` 자동 감지 고도화

현재 방식은 프로젝트 루트와 `notebooks` 폴더 실행만 가정한 단순 구조입니다. 초보자용 교재에서는 충분히 이해 가능한 방식입니다. 더 견고한 파일 존재 기반 탐색은 실무적으로 좋지만 필수는 아닙니다.

---

### [4-2] 특정 LLM 도구 안내

ChatGPT, Claude, Gemini 등 예시는 가능하지만 서비스명, URL, 무료/유료 정책은 자주 바뀝니다. 교재 본문에는 “사용 가능한 LLM 도구 중 하나를 선택” 정도로 쓰고, 실제 수업에서는 강사가 최신 도구를 안내하는 방식이 더 안전합니다.

---

### [4-3] f-string과 `.format()` 혼용

혼용 자체는 문제가 아닙니다. 재사용 템플릿은 `.format()`, 현재 변수값을 즉시 넣는 문장은 f-string을 쓰는 방식이 자연스럽습니다. 두 방식의 차이를 처음 등장할 때 한 문단으로 설명하면 충분합니다.

---

### [4-4] `~~~` 코드 펜스

`~~~`는 Markdown에서 허용되는 코드 블록 문법입니다. 백틱 3개와 비교해 호환성 차이가 있을 수는 있지만 “비표준 오류”라고 단정하기 어렵습니다. 따라서 반영 제외 가능 항목입니다.

---

### [4-5] 연습 문제 채점 기준과 핵심 용어 정리

있으면 좋지만 필수 오류는 아닙니다. 프로젝트 과제 운영 시에는 별도 채점 루브릭 문서로 제공해도 됩니다.

## 6. 전반적 평가

ch09는 이 교재에서 중요한 전환점이 되는 장입니다. 이전 장들이 pandas 중심 분석을 다루었다면, ch09는 LLM을 분석 보조 도구로 활용하면서도 원본 데이터 보호, 프롬프트 구조화, LLM 답변 검증, 활용 기록까지 포함합니다. 방향성은 매우 좋습니다.

후속 본문 수정에서 가장 먼저 볼 부분은 두 가지입니다.

1. 수업 시간 설명을 실제 운영 시간과 맞추기
2. Notebook 파일명을 실제 파일과 일치시키기

그다음으로는 LLM이 잘못된 코드를 제안하는 예시와 사람이 이를 검증·수정하는 과정을 추가하면 장의 완성도가 크게 올라갑니다.
